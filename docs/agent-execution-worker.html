Agent Execution Worker

How a queue-backed workflow engine runs an AI agent step: start the execution, keep its id on a queued job, and poll until it finishes or its deadline expires. The platform never blocks, so every call returns at once and the waiting happens in the queue. The full specification — all 34 WRK-NN requirements, with diagrams. 01 The two rules

Everything else follows from these

The worker's whole job is to turn one agent step into exactly one execution on the platform, and to report what happened to it. Two rules constrain every code path below. If you read nothing else, read these.

R1

One execution per attempt. Once the worker holds an execution id, no code path may start another execution for that attempt.

Not on a retryable failure, not on a failed cancel, not on a redelivered job, not at the deadline. Re-running an agent costs a second model call and can repeat its side effects. Only a new attempt, created above the worker, may start a new execution.

R2

A crash must never produce a second run. Every start call carries an idempotency key derived from the attempt.

A redelivered job re-sends the same key, and the platform replays the recorded execution instead of starting a new one. This is what makes the dangerous window — the platform created the execution, then the worker died before writing down its id — safe.

Start returns at once
The platform answers with an execution_id and a status whether or not the agent has finished.
The queue does the waiting
One job per tick — one turn of the loop: a single status read, then a decision. The delay between ticks is a row in Postgres, not a sleeping worker, so it costs no capacity and survives a restart.
Backoff paces polls only
Exponential with jitter, capped. There is no backoff curve for re-running agents, because the worker never re-runs one.
Deadline cancels
When time runs out the worker cancels the execution, then fails the step, so the agent stops spending.

02 Terms

The nine words this page leans on

The same definitions as section 1.4 of the written spec. The one worth reading twice is tick, which carries most of the design.

Tick
One agent.poll job — one turn of the polling loop: a single status read, then a decision. A tick takes milliseconds however long the agent runs.
Step
One agent invocation inside a workflow run, identified by run_id + step_id.
Attempt
One try at a step. A new attempt is created above the worker and starts a new execution; the worker never creates one.
Execution
The platform's record of one agent run, identified by an execution_id.
Terminal
An execution in succeeded, failed, or cancelled. It will not change again.
Deadline
The wall-clock time after which the worker stops waiting for a step's execution.
Queue
A named lane of jobs stored in Postgres by pg-boss. The name is an arbitrary string this spec chose, not a library concept.
Job
One unit of work on a queue, carrying a JSON payload.
Handler
The function a worker registers for a queue. Resolving completes the job; throwing fails it.

03 Architecture

Four moving parts

The engine hands off a step and never blocks on it. The worker owns two handlers that talk to the platform and to each other only through the queue, so any of them can crash between steps without losing the execution.

The execution itself lives entirely on the platform. The worker holds only its id, which is why losing that id at the wrong moment is the one genuinely dangerous failure — and why R2 exists.

04 Platform requirements

What the worker needs from the other side

These are dependencies, not designs. The contract in this repo (api/openapi.yaml) satisfies all seven; a platform that satisfies none of them cannot be driven by this worker at all.

WRK-01

Non-blocking start. Starting an execution returns immediately with an execution_id and a status, whether or not the agent has finished.

A platform that answers only once the agent completes has nothing for the worker to hold on to, and nothing to poll.

WRK-02

Status by execution id. Querying an execution by id returns its current state at once, including the terminal result once it exists.

This is the polling primitive. Without it there is no loop.

WRK-03

Idempotent start. A start request carries a caller-supplied idempotency key; re-sending the same key with the same body starts nothing and returns the recorded execution with its original id.

This is what makes R2 hold. Everything in Crash recovery rests on it.

WRK-04

Idempotency retention outlives queued jobs. Recorded keys are kept longer than the longest a job can sit in the queue before delivery.

The reference contract keeps them at least 24 hours, so the engine's job retention must be configured below that. Past the window, a redelivery can no longer replay and would start a second execution.

WRK-05

Cancellation by execution id, and it is idempotent.

Cancelling an execution that has already finished is not an error. The worker needs this at the deadline, when nobody is waiting for the result any more.

WRK-06

Explicit retryability on errors. Every error says whether retrying can succeed, and rejections that ask the caller to wait carry Retry-After.

The worker then classifies outcomes without maintaining its own table of error codes, and a new code the platform adds later still classifies correctly.

WRK-07

Rate-limit signalling on responses.

A fleet of pollers can then slow down before it is throttled rather than after.

Execution shape. The worker reads only execution_id, status (queued, running, succeeded, failed, cancelled), output or error, and trace_id. It must not depend on usage, model, latency, or timestamp fields, which the contract does not carry.

05 Job model

Two queues, one tick at a time

The names are ours
agent.start and agent.poll are queue names this spec picked. In pg-boss a queue is a named lane of jobs in Postgres, and the name is any string — the dot is only a grouping convention.
Three calls
createQueue(name) once at startup, send(name, data, options) to enqueue, work(name, handler) to consume.
Resolve or throw
A handler that resolves completes its job; one that throws is failed and retried under the queue's policy. That is why "still running" must never throw.
Options used here
startAfter delays a job. singletonKey allows only one job per key in the created, retry, or active state. retryLimit governs failed jobs.
agent.start run_id, step_id, attempt, agent_id, agent_version, input, timeout_ms, deadline_at

Sent by the workflow engine, once per attempt. Its handler calls the platform, records the execution_id, and enqueues the first poll. Safe to redeliver.

agent.poll execution_id, run_id, step_id, attempt, deadline_at, poll_count

Sent by the worker itself, once per tick — this queue feeds itself. Its handler does one status query, then either finishes the step or schedules the next tick with startAfter. Enqueued with singletonKey: execution_id so one execution can never have two poll chains.

Why the wait lives in the queue

WRK-10

Two job types, with the payloads above.

deadline_at is an absolute timestamp, computed once at the start call and copied onto every poll job so it cannot drift.

WRK-11

One poll job per tick. A poll job performs exactly one status query, then completes; if the execution is still running it enqueues the next tick with startAfter.

The worker must not sleep inside a job. A sleeping handler holds its worker for the whole agent run, and pg-boss defaults to one worker per queue per process — fifty in-flight executions would need fifty idle slots. Its timer also dies with a deploy, while the job stays active until expireInSeconds lapses.

WRK-13

One poller per execution. Poll jobs are enqueued with singletonKey set to the execution_id.

Two poll chains are not dangerous — polling is a read — but they double the request rate and race to complete the step. pg-boss allows only one job per key in the created, retry, or active state, so the duplicate is discarded rather than queued.

WRK-12

"Still running" is a successful job, not a failure.

The worker must not throw to schedule the next poll, and must not lean on the queue's retry machinery for it. Conflating the two makes every slow agent look like a failing job: failure metrics become meaningless and healthy work eventually lands in the dead-letter queue. Job retries are reserved for call failures — unreachable platform, 5xx, 429.

WRK-14

Both queues are declared with createQueue at startup, before anything is sent to them.

pg-boss v10 and later do not create a queue implicitly on send, so a worker that skips this fails on its first enqueue. On majors before v10 the call is harmless, so make it unconditionally.

WRK-15

Set expireInSeconds per queue rather than inheriting the 15-minute default.

A tick whose worker died stays active until that window lapses. Poll ticks are millisecond reads, so a minute is generous — left at the default, a crash mid-tick stalls that step for a quarter of an hour before anything retries it.

06 Starting

The key is the whole trick

WRK-20

The idempotency key is a pure function of the attempt: key = f(run_id, step_id, attempt).

No timestamp, no random value, no retry counter — a redelivered job has to reproduce it byte for byte. A new attempt produces a new key, which is the only mechanism by which a step ever runs an agent twice.

WRK-21

Send the key on every start call, including retries of the call itself.

Sending it only on the first try defeats WRK-03 exactly when it is needed: the retry after an uncertain failure.

WRK-22

Handle both start outcomes.

Already terminal (a fast agent, or a replay of a finished execution): record the outcome and complete the step, enqueueing no poll. Not terminal: record the execution_id, then enqueue the first tick.

WRK-23

Retry call failures, bounded. A transport failure, 5xx, or 429 on the start call is retried with the same key, up to a configured limit.

Because the key is stable, a retry following a request the platform did process returns the existing execution rather than creating a second one. A rejection that is not retryable — invalid input, unknown or disabled version, a key reused with a different body — fails the step immediately and must not be retried.

If the start call answers with an execution that is already terminal — a fast agent, or a replay of one that has since finished — the worker records the outcome and enqueues no poll at all.

07 Polling

One query, one decision

Every tick ends in exactly one of four ways. The branch that is easy to get wrong is the middle one: a failed query is not a failed step, because the execution is still running on the platform regardless of whether the worker could reach it.

WRK-30

One query, one decision. Each tick reads the execution once, then does exactly one of: write the outcome and finish; enqueue the next tick; or run the timeout path.

Nothing else belongs in a tick. Keeping it to one read and one decision is what makes a tick cheap enough to repeat after a crash.

WRK-31

Never start an execution from a poll job.

R1 expressed in the one place it is most tempting to break: a tick that finds a retryable failure must report it, not restart it.

WRK-32

A failed query does not end the step. If the status read itself fails, the execution is still running on the platform and the step is still live.

The worker retries the read up to the deadline; only the deadline ends a step whose platform state is unknown. An execution id reported as not found is different: the record is gone, so the step fails at once rather than polling a ghost.

WRK-33

Carry the poll count in the job payload.

poll_count drives the backoff curve; keeping it in the payload means the curve survives redelivery without a database read.

08 Backoff

Exponential, capped, jittered

delay = min(max_delay, base × factorpoll_count), then scheduled at a random point in [0, delay]. Fast agents finish in the first tick or two; slow ones settle into a cheap steady rate instead of hammering the platform for minutes.

TickNominal delayScheduled atElapsed
11srandom(0, 1s)~1s

These delays are floors, not exact times. Workers find due jobs by polling, so the real gap is the scheduled delay plus up to pollingIntervalSeconds (default 2). A 1-second backoff lands in roughly one to three seconds, and an interval below a second buys nothing.

WRK-40

Exponential with a cap. delay = min(max_delay, base × factorpoll_count), defaults 1s, 2, 30s.

Fast agents finish within a tick or two; slow ones settle into a cheap steady rate rather than hammering the platform for minutes.

WRK-41

Jitter is required, not a refinement.

A workflow that fans out starts many steps in the same instant. Without jitter they poll in lockstep for as long as they live, turning smooth load into periodic spikes that trip the platform's rate limits — and the retry after a 429 re-synchronises them, so the spikes persist.

WRK-42

A Retry-After header outranks the computed delay whenever it is longer.

The platform's own signal wins. The same goes for rate-limit headers showing the window nearly spent.

09 Deadline

Cancel, then fail

WRK-50

Cancel, then fail. When the deadline passes with the execution still running, cancel it and then fail the step with a timeout error.

Cancelling first stops the agent spending on a result nobody is waiting for.

WRK-51

Cancel is best-effort. A cancel that fails must not mask the timeout.

The step still fails with the timeout error and the cancel failure is only logged. Cancel may be retried a few times, and a cancelled execution may briefly still report running — that is expected, and it is not polled further.

WRK-24

deadline_at is computed once, before the first start call, and never recomputed.

It rides along on every poll job, so it survives redelivery. Recomputing it on redelivery would let a crash-looping job extend its own deadline indefinitely — the step would never time out.

10 Outcomes

Every row answers "no"

This table is R1 in full. Whatever the platform says, the worker's answer to "should I start another execution?" is the same.

Platform stateStep outcomeStart a new execution?
succeededSucceeded, with outputNo
failedFailed, marked retryable for the layer aboveNo
failedFailed, terminal (not retryable)No
cancelledCancelled — not a failure, not error-routedNo
Still running at the deadlineTimed out, after cancelNo
Execution id not foundFailed, terminal (record lost)No
Status query failedNo outcome yet — retry until the deadlineNo

A retryable failure is reported, not retried. The layer that owns attempts may then create attempt n+1, which produces a new idempotency key and, only then, a new execution.

WRK-52

The mapping above is the contract between platform state and step outcome.

cancelled is the row people get wrong: it is not a failure, and must not be routed to a step's error handling. It is the one terminal state the caller caused.

WRK-53

Record the result once. Writing a step's outcome is idempotent, keyed by run_id + step_id + attempt.

A duplicated final tick must not produce two results or two completion events. This is what makes the last crash window in Crash recovery harmless.

11 Crash recovery

The dangerous window, and why it closes

Crash pointOn redeliverySafe because
Before the start call is sentCall is sent for the first timeNothing happened yet

WRK-60

Redelivery is normal, not exceptional. The queue may deliver any job more than once, and every job type above is safe under that.

The table shows each crash point and what makes it safe. None of them needs a distributed lock or a reconciliation sweep.

WRK-61

Never infer "no execution exists" from "no id recorded".

That single inference is what creates duplicate runs. The only safe recovery is to re-send the key and let the platform answer — it is the one party that knows.

WRK-62

Job retention must stay below the platform's idempotency retention.

If a job can sit in the queue longer than the platform remembers keys, a very old redelivery can no longer replay — it would start a second execution. The worker also refuses to start an execution for a job whose deadline_at has already passed, which discards such jobs instead.

12 Observability

What to keep, and what it tells you

WRK-70

Store the correlation id. trace_id is written with the step result.

An engineer can then open the platform's trace for a failed step instead of searching by timestamp. It is the only correlation the execution carries — there is no usage, model, latency, or timestamp field.

WRK-71

Metrics worth having: polls per execution, time from start to terminal, timeouts, cancels, replayed starts, and duplicate poll suppressions.

Two of these are diagnostic rather than decorative. Polls per execution shows whether the backoff curve is tuned — a median in the low single digits with a long tail is healthy. Replayed starts should be near zero; a rising count means workers are crash-looping between the start call and recording the id.

15 Open questions

Worth settling with the platform team

Q1 · recovery

There is no "find the execution for this key" operation, so recovery depends entirely on replay. An explicit lookup would let a worker reconcile an orphan it never recorded.

Q2 · retention

The assumed idempotency retention is at least 24 hours. Job retention must be configured below the real figure.

Q3 · progress

Nothing carries partial output or progress, so a long-running agent shows only running to an operator. Progress needs a platform-side field first.

Q4 · fan-out

A step mapping an agent over many items means one execution and one poll chain per item. A batch start would cut request volume considerably.
