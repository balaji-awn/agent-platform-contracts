How Agent Execution Works

A workflow needs to run an AI agent. The agent might take two seconds or four minutes, it costs money every time it runs, and the machine asking for it may be restarted halfway through. This is how such a thing is made to work reliably — the ideas first, then the mechanics, with diagrams throughout. No prior knowledge assumed.

01 The problem

Waiting is the hard part

Imagine a workflow that handles a security alert. One of its steps asks an AI agent to read the alert and judge how serious it is. That step is easy to describe and surprisingly hard to run, for three reasons.

It takes an awkward amount of time. Not milliseconds, so you cannot simply wait for it inside a function call. Not hours, so a nightly batch is overkill. Somewhere between a second and several minutes — long enough that something will go wrong while you wait.

It costs real money each time. Running the agent twice by accident is not a tidy little bug; it is a second bill, and possibly a second set of actions taken in the outside world.

The thing doing the waiting is not reliable. Servers get restarted for deployments, processes crash, networks drop connections at the worst possible moment. Any design that assumes "the program stays alive until the answer comes back" will lose answers in production.

The core tension

Something that takes minutes has to be supervised by something that can die at any second.

Everything that follows is a way of making the supervision disposable — so that losing the supervisor costs nothing, because the important state was never in it.

The AI platform helps by refusing to make anyone wait. When you ask it to run an agent, it answers immediately with an identifier and a status, rather than holding the line open until the agent is finished. That single design choice is what makes everything below possible: the work gets an address, and anyone can ask about it later.

02 The words

Six terms, then we can talk

These are used throughout. None of them is complicated, but they have precise meanings here.

Execution
One run of an agent, living on the AI platform. It has an id, and you can ask about it by that id at any time.
Queue
A to-do list stored in a database. Programs add items to it; workers take items off it. Because it is in a database, it survives restarts.
Job
One item on that to-do list, with a little data attached. A job can be scheduled for later rather than right now.
Worker
A program that takes jobs off a queue and does them. There may be many, and any of them may be restarted at any time.
Check
One glance at an execution: ask the platform how it is doing, then decide what to do about the answer. Takes milliseconds.
Deadline
The moment after which we stop waiting for a particular execution, however it is getting on.

The whole design is: start an execution, then perform checks on it until it finishes or the deadline passes. The interesting questions are where the waiting between checks lives, how often to check, and what happens when the checker dies.

03 The shape of it

Four parts, and only one of them remembers anything

Two things are worth noticing in that picture.

The agent's work happens entirely on the platform. The worker holds nothing but an id. If every worker were to disappear for ten minutes, the agent would carry on regardless, and the result would be waiting when someone came back to ask.

Only one arrow creates anything. "Start it" brings an execution into being. Every other arrow is a question or an answer. This matters enormously later: questions are safe to repeat, and creation is not.

04 A run, end to end

What actually happens, in order

Each visit follows the same tiny script: ask once, then decide exactly one thing. Either the execution has finished, in which case record the outcome and stop; or it has not, in which case book another visit for later; or time has run out, which has its own handling. That is the entire loop.

05 Where waiting lives

The most important decision in the design

Suppose the next check should happen in thirty seconds. There are two ways to arrange that, and they look equally reasonable until you examine them.

The obvious way: the program sleeps for thirty seconds, then checks again. The waiting lives inside the running program, as a timer in memory.

The way used here: the program finishes, having left a note in the database that says "check this execution, not before thirty seconds from now". The waiting lives in the database, as a row.

 Sleeping in the programA note in the database
Where the wait exists A timer in one program's memory A row, visible to every worker
While waiting That program is occupied and cannot do anything else Nothing is occupied at all
If it is restarted The wait is lost and the work stalls until something notices Nothing happens — the row is still there, and any worker can pick it up
Cost of 500 at once 500 programs sleeping 500 rows, and a handful of brief visits per second
Why this is the crux

A sleeping program is a promise that only that program can keep. A row in a database is a promise anyone can keep.

Deployments, crashes and scaling all become uneventful the moment no promise depends on a particular process staying alive.

There is a second benefit, easy to miss. When the waiting lives outside the program, the number of executions you can supervise stops depending on how long agents take. A worker that would be tied up by fifty simultaneous four-minute agents can, in this arrangement, look after thousands — because it is only ever doing a few milliseconds of work at a time.

06 Pacing the checks

Often at first, then increasingly rarely

How often should we look? Checking every second is wasteful: most of those questions get the answer "still running". Checking every thirty seconds is rude to fast agents, which would finish in two seconds and then sit around unnoticed for twenty-eight more.

The usual resolution is to start impatient and grow steadily more relaxed: wait one second, then two, then four, eight, sixteen, and so on up to a sensible ceiling. Fast agents are caught almost at once; slow ones settle into a cheap rhythm rather than being pestered.

The ceiling matters as much as the doubling. Without it, an agent that runs for an hour would eventually be checked once every twenty minutes, and a result that arrived early in that gap would sit unnoticed. A cap of about half a minute keeps the worst-case delay small while keeping the number of questions modest.

07 The stampede problem

Why the waits are deliberately imprecise

Here is a failure that only appears at scale. A workflow fans out and starts forty agents at the same instant. Each one follows the same schedule: check after one second, then two, then four. Which means all forty ask their questions at the same moments, forever. The platform sees nothing for four seconds, then forty questions in the same breath, then nothing again.

Worse, the obvious defence makes it permanent. If the platform pushes back and everyone waits and retries, they all wait the same amount and retry together — the herd is re-formed by the very mechanism meant to disperse it.

The fix is to make each wait deliberately imprecise. Instead of waiting exactly four seconds, wait a random amount between zero and four. The average pace is unchanged, the schedule is just as predictable in aggregate, but the clients smear out across the interval instead of arriving together.

The general lesson

Synchronised clients are an emergent problem: each one behaves perfectly sensibly, and the system misbehaves anyway.

Randomness is not sloppiness here. It is the cheapest known way to stop independent actors from accidentally marching in step.

08 When things crash

The one genuinely dangerous moment

Queues promise that a job will be delivered at least once. They cannot promise exactly once: if a worker takes a job and then vanishes, the queue has no way to know whether it finished the work first. So it hands the job to somebody else. This is the right behaviour — losing work would be worse — but it means every job must be safe to do twice.

For checks, that is trivially true: asking a question twice is harmless. For starting an agent, it is the whole problem. Consider this sequence:

  • The worker asks the platform to start an agent.
  • The platform does so, and begins running it.
  • The worker dies before it can write down the id.

The replacement worker now faces a question it genuinely cannot answer from its own knowledge: did that request ever reach the platform? "I have no id written down" is consistent with both "nothing happened" and "something happened and I lost the receipt". Guess wrong in one direction and you have two agents running and two bills; guess wrong in the other and the step hangs forever.

The rule that resolves it

Never infer "nothing was started" from "I have no record of starting anything".

The worker's memory is not the authority. The platform is. So ask the platform — but ask in a way that cannot accidentally start a second run.

That way is an idempotency key: a label attached to the request, derived purely from which step and which attempt this is, so that the replacement worker computes the identical label. The platform promises that two requests bearing the same label produce one execution. The second request does not start anything; it returns the first one's details.

This is worth pausing on, because it is a general technique. Exactly-once execution across a network is impossible for the sender to guarantee alone — it can never distinguish a lost request from a lost reply. What is possible is for the receiver to recognise a repeat and decline to act twice. The key is how the sender makes itself recognisable.

09 When time runs out

Stopping is also a decision

Every step carries a deadline, fixed at the moment it starts and carried along with every subsequent check. When a check finds that the deadline has passed and the agent is still going, two things happen, in this order: the worker asks the platform to stop the execution, and then records the step as having run out of time.

The order matters. Cancelling first means the agent stops consuming time and money on a result that nobody is going to read. Recording the outcome second means the workflow finds out promptly either way, because the cancellation is a courtesy, not a precondition.

Fixing the deadline once, at the beginning, is a small detail with a sharp edge behind it. If instead each worker recalculated "now plus four minutes" when it picked the job up, a job that kept crashing and being redelivered would keep pushing its own deadline into the future, and would never time out at all.

10 How a run ends

Four endings, and one temptation to resist

Failures come in two flavours, and the platform says which is which. Some are worth another go: the model provider was briefly overloaded, a rate limit was hit. Others will fail identically forever: the input did not match what the agent expects. Retrying the second kind just burns money to arrive at the same place.

The temptation

When a check discovers a failure that could succeed on a retry, the obvious move is to start the agent again right there. The worker never does this.

Retrying is a policy decision about the workflow — how many attempts are worth paying for, whether a fallback path is better — and it belongs with whoever owns that policy. The worker reports what happened and lets that layer decide.

When that layer does decide to try again, it does so by creating a genuinely new attempt. That new attempt computes a different label, so the platform treats it as new work rather than replaying the old failure. The distinction between "the same attempt, asked about again" and "a deliberate new attempt" is carried entirely by that label, which is why it is built the way it is.

11 What it costs

Some arithmetic, because the intuitions mislead

"Polling is wasteful" is received wisdom, and at a fixed one-second interval it would be. With doubling and a ceiling, the arithmetic looks different.

Agent takesFixed 1s checksDoubling, capped at 30sDifference
3 seconds32Barely matters
47 seconds4768× fewer
5 minutes3001421× fewer
30 minutes18006428× fewer

Put that next to the number of agents you expect to have running at once. Five hundred simultaneous executions, each being checked roughly every thirty seconds once they settle, comes to about seventeen questions per second across the whole fleet. That is a rounding error for a web service, and it buys a system with no open connections to lose and no timers to forget.

The comparison that really matters is not against a hypothetical push-based design, but against the sleeping version of this same design. Both ask the platform a similar number of questions. Only one of them ties up a process per execution while doing it.

12 Where the limits are

What this design does not give you

Every design buys something and gives something up. Three things are given up here, and it is better to know them in advance than to discover them.

No progress, only presence
Between checks an execution is either running or finished. There is no "62% done" and no partial output, so a long-running agent looks identical at ten seconds and ten minutes.
Answers arrive a little late
A result that appears just after a check is not noticed until the next one, which near the ceiling can be up to half a minute later. Fine for a workflow step, wrong for anything interactive.
Fan-out multiplies everything
A step that runs an agent over two hundred items means two hundred executions, each with its own chain of checks. Nothing breaks, but the request volume is worth a thought.

Each of these has an obvious remedy if it ever becomes painful — progress events, a push notification for the impatient cases, a batch call for fan-out. None of them is needed for a workflow engine running agent steps, and each would add a moving part. The version described here is the one that has the fewest ways to go wrong.

The whole thing in four sentences

Ask the platform to start an agent, and it hands back an id straight away. Keep that id on a queued job, and check on it now and then — often at first, then more sparingly, with a dash of randomness so that many steps do not synchronise.

If a worker dies, the job comes back and the same label gets the same execution rather than a second one. If the deadline passes, stop the execution and say so — and never quietly run an agent twice.
