Agent Platform API Reference

Every endpoint the agent platform exposes to Asoar, field by field: what each parameter is, what comes back, and why the contract is shaped this way. The reasoning is included because most of these fields exist to survive a specific failure — a redelivered queue job, a hung model call, a cancelled run — and that is not recoverable from the field name alone.

Conventions

These hold for every operation, so they are stated once here rather than repeated in each endpoint below.

Authorization header · bearer required

A service-to-service token. One credential for the whole Asoar backend, not per end user.

WhyAsoar has no user-level authn yet, and the designer runs in a browser. A single server-side credential keeps platform tokens out of the browser entirely. Whether this becomes OAuth client credentials or a scoped API key is still open.

X-Tenant-ID header · string required

The tenant the work belongs to. Agents, versions, and executions are scoped to it, and anything the tenant cannot see returns 404, never 403.

Why a header, not a body fieldOne service credential serves every tenant, so the tenant has to travel per request. Keeping it in a header rather than inside the execution body means it never participates in the idempotency body comparison, and an edge proxy can route or meter on it without parsing JSON. 404 instead of 403 avoids confirming that another tenant's agent exists.

RateLimit-Limit RateLimit-Remaining RateLimit-Reset response headers

Present on every response, including errors. Reset is in seconds.

Why on every responseAsoar paces a job queue, not a UI. Knowing the remaining budget on the responses it already makes lets the engine slow down before it starts collecting 429s; headers only on success would hide exactly the moment throttling matters.

Compatibility

Response objects may gain fields and Error.code may gain values; clients ignore what they do not know. Request bodies are closed — an unknown field is 400 REQUEST_INVALID.

Why asymmetricThe two directions have opposite risks. A new response field must never break a deployed caller, so responses stay open. An unrecognised request field usually means a typo or a version mismatch in the caller; silently dropping it would let a workflow run with settings nobody applied.

Failure channels

Every failure arrives through one of two channels, and callers handle them differently. This distinction drives the response codes of every execution endpoint.

 Request-level rejectionExecution-level failure
Meaning The request was refused before an execution existed. The execution was created and reached status: failed.
HTTP Non-2xx with an ErrorEnvelope 200 with an Execution whose error is set
Side effects Nothing created. The Idempotency-Key is not recorded, so the same key may be sent again. The execution is recorded and billable work may have happened.
Typical codes INPUT_SCHEMA_INVALID, AGENT_VERSION_DISABLED, QUOTA_EXCEEDED TIMEOUT, OUTPUT_SCHEMA_VIOLATION, PROVIDER_UNAVAILABLE

Why two channels instead of oneCollapsing them would make a 4xx ambiguous: the caller could not tell whether an execution exists, which decides whether retrying with the same idempotency key is safe and whether anything needs cancelling. A failed execution is a result — it has an id, usage, and a trace — so it is returned as one.

Idempotency

Asoar's engine runs on a durable queue. A worker can die mid-execution and the job will be redelivered; that redelivery must not start a second model run or produce a second bill. Asoar builds the key as run_id + node_path + attempt.

Scope

Keys are scoped per tenant and retained at least 24 hours after the execution is created.

Why per tenantKeys are caller-chosen strings. Two tenants can pick the same one, and a cross-tenant collision would leak one tenant's execution to another. The retention window is a proposal — it bounds how long a delayed job can still be replayed safely, and the platform team needs to confirm what they can hold.

Same key, same body

Returns the recorded execution in its current state, starts nothing, and honours Prefer: wait again. Bodies are compared as JSON values after RFC 8785 canonicalization.

Why canonical comparison, not bytesThe body is re-serialized by the caller on redelivery, and map ordering, whitespace, and number formatting are not stable across encoders. A byte comparison would report a conflict for a request that is semantically identical — turning a routine redelivery into a hard failure.

Same key, different body

409 IDEMPOTENCY_KEY_REUSED, non-retryable.

Why an error rather than a new runIt means two different node inputs collided on one key, which is a bug in key construction. Executing would double-bill and write the wrong result into a checkpoint; failing loudly surfaces it in one run instead of silently corrupting many.

attempt in the key

Incremented only when the engine deliberately retries after a terminal failure.

Why it must be thereWithout it, a deliberate retry would match the original key and get the old failed execution back forever, making retries useless. With it, a redelivery (same attempt) replays and a retry (new attempt) genuinely re-runs.

Ordering against other checks

Replay is resolved before the agent version is checked, so a replay succeeds even if the version was disabled in the meantime.

Why replay winsThe execution already ran and may already be billed. If a redelivery after a version was disabled returned 409, a finished result would become permanently unreachable and the run would fail for a reason that has nothing to do with it.

Prefer: wait

POST /executions and the test endpoint are hybrid sync/async. The server holds the request open up to wait=N seconds for a terminal state, then answers 200 with the execution, or 202 if it is still running.

Prefer header · string optional e.g. wait=20, respond-async, wait=20

Parsed as RFC 7240. Other preferences are ignored, and a wait value that is not a non-negative integer is ignored rather than rejected. Without it the server does not wait.

Why a wait window at allMost agent runs finish in seconds. Forcing every caller into submit-then-poll would double the round trips and add poll latency to every fast run, while holding the connection open for slow ones would exhaust sockets. The window lets one endpoint serve both without the caller choosing in advance.

Why ignore a malformed valueRFC 7240 preferences are hints. Rejecting the whole execution because a proxy mangled a hint would turn a cosmetic problem into a failed workflow node.

Preference-Applied response header

wait=N, the whole seconds the server was actually willing to wait after applying its own cap.

Why echo itThe server may cap the window. Without the echo, a caller that asked for 60s and silently got 5s cannot tell a slow agent from a short cap, and will size its poll interval wrong.

Location response header · 202 only

URI reference to the execution resource, resolved against the request URL.

WhyIt lets a generic HTTP client follow the async result without knowing how to build the polling URL from the id.

Design-time operations

These back the designer's agent palette, the inline preview, the About and Settings tabs, and the publish validator. Asoar's backend proxies them; the browser never calls the platform.

GET /agents listAgents

A lightweight list for the palette, in a stable order. Deliberately does not include schemas.

Why no schemas hereA palette can hold hundreds of agents, and their input and output schemas are the largest part of a contract. Shipping them on every keystroke of a search box would make the list slow for data the designer only needs once an author opens one specific agent.

Query parameters
searchstringoptional

Case-insensitive substring match on agent_id, name, or description.

Why all three fieldsAuthors look for agents by what they do ("triage"), not by id. Matching the description too means a useful agent is findable before anyone has learned its name.

tagsarray, comma-separatedoptional

Keeps only agents carrying every listed tag.

Why AND, not ORTags are used to narrow a long list. OR semantics would grow the result with each tag added, which is the opposite of what someone filtering expects.

statuspublished | deprecateddefault published

Keeps agents with at least one version in this status.

Why no disabled optionThe palette exists to pick an agent to run. A disabled version cannot run, so listing it would only produce a node that fails at publish. Deprecated is offered because authors sometimes need to find an agent they already depend on.

cursorstring, opaqueoptional

The next_cursor of a previous page. An invalid cursor is 400 REQUEST_INVALID.

Why opaque rather than an offsetIt lets the platform change its pagination internals — offset, keyset, or a search cursor — without a contract change, and stops callers from synthesising positions that skip or duplicate rows.

limitinteger 1–200default 50

Page size.

Why cappedThe cap bounds the worst-case response for a tenant with a very large catalog, so one palette request cannot become an expensive query.

Responses

Why a caller-visible id rather than a UUIDWorkflow nodes pin agent_id@version and that pin is stored in workflow JSON and read by humans during review. A readable id makes a diff of a published workflow legible.

GET /agents/{agent_id}/versions listAgentVersions

Every version in every status, newest first, as AgentVersionSummary objects.

Why every status, including disabledThis is what powers the "vN available" badge and the upgrade flow. A node pinned to a version that has since been deprecated or disabled must be able to discover that, which is impossible if the list hides those versions.

Why newest firstThe most common question is "is there anything newer than my pin", so the answer is the first row.

Responses
StatusBody
200{ items: AgentVersionSummary[] } — version, status, digest, published_at.
404AGENT_NOT_FOUND

Why the digest appears in the summaryIt lets the designer detect drift without fetching every full contract: compare the digest stored on the node with the one in this list.

GET /agents/{agent_id}/versions/{version} getAgentVersion

The full contract: input schema, output schema, limits, digest, and model details. This is the source of truth Asoar re-fetches at workflow publish, and it is returned for a version in any status.

Why publish re-fetches instead of trusting the nodeThe node carries a snapshot taken when the author dropped the agent, possibly weeks earlier. Trusting it would let a workflow publish against a contract that no longer exists. The platform is authoritative, so publish asks it again and compares digests.

Path parameters
versioninteger ≥ 1required

The pinned version number. A value that is not a positive integer is 400 REQUEST_INVALID.

Why an ordinal integer, not a labelOrdering carries meaning here: the designer computes "newer than my pin" by comparing numbers. Opaque version strings would make that a lookup, and semantic version strings would invite range pinning, which is exactly the floating-version behaviour the design rejects.

Responses
StatusBody
200AgentVersionContract
404AGENT_VERSION_NOT_FOUND, for an unknown agent, unknown version, or one not visible to the tenant.

POST /agents/{agent_id}/versions/{version}/test testAgentVersion

A sample run from the designer's Test tab. Behaves exactly like createExecution — same order of checks, same failure channels, same Prefer: wait handling — with four differences.

Differences from createExecution
is_testflag on the execution

The returned execution is flagged and excluded from production metrics.

Why flagged rather than a separate pipelineA test must exercise the real model, the real schemas, and the real limits, or it proves nothing. Only the accounting differs, so the run is identical and the flag keeps designer experiments out of production dashboards and cost rollups.

no Idempotency-Key

There is no key and no replay.

WhyA human clicking "Run" wants a fresh run each time. Replay semantics would return a cached result and make the button look broken.

no context

There is no workflow_id, run_id, or node_path.

WhyA test happens on a draft, before any run exists. Requiring correlation ids would mean inventing fake ones that then pollute traces and billing records.

timeout_msinteger ≥ 1000optional

Defaults to the version's default_timeout_ms. Still may not exceed max_timeout_ms.

Why optional here but required at runtimeThe designer is testing the agent, not a node's execution policy, and the author may not have configured one yet. At runtime the node always has a policy, so leaving the timeout implicit there would hide a value that governs a production run.

Runtime operations

One agent node in a running workflow becomes one execution here, driven by a queue worker that may be restarted, retried, or cancelled at any moment.

POST /executions createExecution

Starts an execution, or replays the one already recorded for this idempotency key. The single most important operation in the contract.

Headers
Idempotency-Keystring, 1–512 charsrequired

Asoar sends run_id + node_path + attempt. See Idempotency.

Why required rather than optionalAn optional safety mechanism is one a caller forgets under pressure, and the failure it prevents — a double-billed duplicate model run after a worker crash — is invisible until the invoice. Making it mandatory means no caller can accidentally opt out.

Why 512 charactersnode_path can be long for a node nested inside loops and sub-workflows. The cap is generous enough for realistic nesting while still bounding what the platform must index.

Preferstringoptional

wait=N. See Prefer: wait.

Request body — ExecutionRequest

Closed to unknown fields.

agent_idstringrequired

The pinned agent.

agent_versioninteger ≥ 1required

The pinned version. Never "latest".

Why the version is mandatoryA workflow that floats on "latest" changes behaviour when someone else publishes an agent, silently breaking bindings and making a completed run non-reproducible. Pinning is what lets an old published workflow keep running unchanged.

inputany JSONrequired

Must conform to the version's input_schema. A mismatch is 400 INPUT_SCHEMA_INVALID with details, and no execution is created.

Why validated before anything runsA schema error fails identically every time, so it must be cheap and non-retryable: rejecting before creating an execution means no model call, no bill, and a free idempotency key.

context.workflow_idstringrequired

The workflow as id@version, e.g. wf_phishing@7.

Why the version is includedCost and failure analysis is almost always asked per published workflow version: "did v7 get more expensive than v6". Without the version the platform can only attribute spend to a workflow in aggregate.

context.run_idstringrequired

The Asoar run this execution belongs to.

WhyIt is the join key for per-run cost rollups and the first thing anyone has when investigating one bad run.

context.node_pathstringrequired

Identifies the node within the run, including loop and sub-workflow nesting.

Why this exact fieldIt is the key Asoar checkpoints results under, and half of the idempotency key. Sending it lets a platform-side trace line up with the exact node a user is looking at in the runs view.

context.attemptinteger ≥ 1optional

Which deliberate attempt this is.

Why it is in the body as well as the keyThe key is opaque to the platform. Having the attempt as a field lets the platform report retry rates per agent without parsing caller-chosen key strings.

timeout_msinteger ≥ 1000required

Per attempt, measured from execution creation. Above the version's max_timeout_ms is 400 REQUEST_INVALID with a details entry for /timeout_ms.

Why the caller sets it and the platform enforces itThe right timeout depends on workflow context — an interactive triage path and an overnight batch tolerate very different waits — so the node owns the value. The platform enforces it because a hung provider call must stop consuming budget even if the caller has already walked away.

Why a floor of 1000msBelow a second, a timeout says more about network jitter than about the agent, and would mostly produce retries that cannot succeed.

callback_urlurioptional

Reserved for the planned completion webhook. Not required for the first version.

Why reserved nowPolling ships first because it is simpler, but the field is in the contract from the start so adding webhooks later is additive rather than a new request shape.

Order of checks

Each of these is a request-level rejection, in this order:

#CheckFailure
1Auth and tenant401 / 403 / 400
2Idempotency-Key present and body well-formed400 REQUEST_INVALID
3Idempotent replay200 / 202, or 409
4Version exists, is visible, is not disabled404 / 409
5timeout_ms within max_timeout_ms400 REQUEST_INVALID
6Input matches input_schema400 INPUT_SCHEMA_INVALID
7Admission (quota, provider capacity)429 / 503

Why the order is part of the contractIt decides what a caller can conclude from a response. Replay before the version check makes redelivery safe after a version is disabled; admission last means a request is only counted against quota once it is otherwise valid, so a malformed caller cannot burn a tenant's budget.

GET /executions/{execution_id} getExecution

The polling endpoint. Returns the current Execution; a failed one is a 200 with status: failed. Unknown or invisible executions are 404 EXECUTION_NOT_FOUND.

Why polling rather than webhooks firstThe queue worker already knows how to sleep and resume, so polling needs no new machinery, no public callback endpoint, and no delivery guarantees. Webhooks are deferred, not rejected — they become worthwhile when executions are long enough that polling wastes real capacity.

Why a 404 is not retryableExecutions are created synchronously by createExecution, so an id that does not resolve will not start resolving later. Retrying would only delay the real failure.

POST /executions/{execution_id}/cancel cancelExecution

Idempotent. A queued or running execution moves to cancelled; cancelling a terminal execution returns it unchanged. Asoar calls this when a run is cancelled and when its own deadline expires.

Responses
StatusMeaning
202Cancellation accepted, or the execution had already finished. The body may still show running.
404EXECUTION_NOT_FOUND

Why 202 and not 200Stopping an in-flight model call is not always instant. 202 says the intent was recorded without claiming the execution is already stopped, which is why the caller is told to poll for the terminal state.

Why a cancelled execution has no errorCancellation is something the caller asked for, not a failure of the agent. Giving it an error object would make it indistinguishable from a real failure and push the workflow down its on-error branch for an intentional stop.

Why it must be idempotentIt is called from two independent paths — run cancellation and deadline expiry — which can fire at nearly the same moment, so duplicate calls are normal rather than exceptional.

GET /executions/{execution_id}/trace getExecutionTrace

Intermediate steps — model calls, tool calls, output repairs — each with type, started_at, optional ended_at and summary. Optional for the first version.

Why it is separate from the executionA trace can be far larger than the result and is only wanted when a human opens one run to investigate it. Keeping it behind its own call means the polling path, which runs constantly, stays small.

Schemas

AgentVersionContract

What a pinned version promises. Returned by getAgentVersion.

input_schemaJSON Schema 2020-12required

The shape of input.

Why 2020-12 specificallyIt is the dialect Asoar already uses for its own action schemas, so agent nodes and integration actions share one binding and validation path instead of two subtly different ones.

output_schemaJSON Schema 2020-12required

The platform guarantees a succeeded execution's output conforms, using structured output plus an internal repair loop.

Why the platform guarantees itDownstream nodes bind to specific output fields at design time. If shape were best-effort, every workflow would need hand-written defensive checks after every agent node. Asoar still re-validates as defence in depth.

limits.default_timeout_msintegerrequired

What the designer pre-fills into a new node.

Why the agent proposes a defaultThe agent's author knows how long it typically takes; a workflow author does not. A sensible pre-fill avoids both 5-second timeouts on a slow agent and 10-minute ones on a fast path.

limits.max_timeout_msintegerrequired

The ceiling. The designer rejects higher values, the publish validator checks again, and the platform enforces it.

Why checked three timesEach layer catches a different mistake: the designer gives immediate feedback, publish catches a workflow edited outside the designer, and the platform is the only place that can stop a request from a caller that skipped both.

limits.recommended_max_attemptsintegeroptional

A hint, not a cap. Asoar's own default is 2.

Why only a recommendationRetries are layered: the platform already absorbs transient provider errors internally, so Asoar retrying aggressively on top multiplies model calls (3 × 3 = 9 for one node). The agent can advise, but the workflow owns the decision.

digeststring, sha256:<64 hex>required

SHA-256 over the RFC 8785 canonical JSON of {input_schema, output_schema, limits}.

Why canonical JSONTwo byte-different serializations of the same schema must produce the same digest, or every re-serialization would look like drift and block publishes for no reason.

Why model details are excludedThe digest answers one question: "do my bindings and settings still hold?" Model and temperature do not affect that. Including them would make a digest comparison fail for a change that cannot break a binding.

statuspublished | deprecated | disabledrequired

deprecated still executes but blocks new pins; disabled rejects executions with AGENT_VERSION_DISABLED.

Why three states rather than twoRetiring an agent needs a phase where existing workflows keep running while new ones are steered elsewhere. Without the middle state, the only options are breaking live workflows or never retiring anything.

modelobjectoptional

Provider, name, temperature, max tokens. Informational, shown read-only in the designer.

Why read-only, with no runtime overrideIf a workflow could override temperature or model, "agent v3" would mean different things in different workflows, and a reported result could not be reproduced from the version alone. Changing the model creates a new version instead.

Execution

The state of one execution, returned by four operations.

statusqueued | running | succeeded | failed | cancelledrequired

The last three are terminal. output is required when succeeded, error when failed.

Why cancelled is its own status, not a failureIt is the one terminal state the caller caused. Asoar must not route it to a node's on-error branch, and it should not count against agent reliability metrics.

usageinput_tokens, output_tokens, cost_usdoptional

Reported per execution.

Why per execution rather than only on an invoiceAsoar journals it per node so a run's cost can be attributed to the node that caused it. An invoice total cannot answer "which node made this workflow expensive". Note that cost_usd is a float today — integer micro-USD would avoid rounding drift in rollups, and is worth settling before anyone depends on it.

trace_idstringoptional

Correlates with the platform's own tracing.

Why returned on the executionIt is journalled with the node result so the runs view can deep-link an engineer straight from a failed node to the platform trace, instead of making them search by timestamp.

latency_msintegeroptional

Present once terminal.

Why the platform reports it rather than the caller measuringThe caller's clock includes queue wait and polling delay. Only the platform can separate how long the agent took from how long Asoar took to notice.

finished_atdate-time or nullrequired

Explicitly null while running.

Why nullable rather than absentAn explicit null distinguishes "not finished yet" from "this platform version does not send the field", which matters for a client that ignores unknown fields by design.

is_testbooleandefault false

True for runs started from the designer's Test tab.

Error model

Every error carries code, message, and an explicit retryable flag. Request-level rejections are wrapped in { "error": … }; execution failures carry the same object inside the execution.

Why an explicit flag instead of inferring from the statusOnly the platform knows whether it already exhausted its internal retries. A 503 might mean "try again in two seconds" or "this execution is finished, stop" — and a caller guessing wrong either gives up on recoverable work or burns attempts on a failure that will repeat identically.

retry_after_msinteger ≥ 0optional

Minimum wait before retrying. Authoritative over the Retry-After header, which carries the same value rounded up to whole seconds.

Why both, and why the body winsThe header exists so proxies and generic HTTP clients behave sensibly. The body field is authoritative because whole seconds are too coarse for a queue scheduling thousands of jobs, and intermediaries rewrite headers.

detailsFieldError[]optional

Each entry has a JSON Pointer path and a message — into the input for INPUT_SCHEMA_INVALID, into the request body otherwise.

Why pointers rather than proseThe designer marks the offending field in the Test tab. A sentence describing the problem cannot be attached to an input control; a pointer can.

OUTPUT_SCHEMA_VIOLATIONnon-retryable

The output did not conform even after the platform's repair loop.

Why non-retryable despite being non-deterministicThe platform has already retried and repaired internally. A further attempt from Asoar mostly repeats work that just failed, and a persistent violation is a contract bug worth surfacing rather than hiding behind retries.

Webhook (planned)

executionFinished would POST { event, execution } to the request's callback_url when an execution reaches a terminal state, where event is one of execution.succeeded, execution.failed, or execution.cancelled. Receivers must treat delivery as at-least-once.

Why it is in the spec but not requiredWriting it down now fixes the payload shape, so the engine can be built to park a node and resume on a callback later without a contract change. It is not required for the first version because polling already works and webhooks add a public endpoint, delivery retries, and signature verification.

Still to settle

Signing and replay protection are unspecified, and the version lifecycle events that would invalidate the catalog cache (agent.version.published / deprecated) are not defined yet.

Deliberately excluded

Things a reader might expect to find here, and why they are absent.

A validate endpoint

Removed from the contract.

WhyIt had no caller. The designer validates locally from the contract snapshot it already stores, and both test and execute reject bad input with INPUT_SCHEMA_INVALID before any model call — so a pre-flight check cost a round trip and saved nothing. Worth revisiting only if platform-side admission grows beyond schema checks.

Per-request model or temperature overrides

Not supported at any layer.

WhyThey would undermine version pinning: the same agent@3 would behave differently in two workflows, and a result could not be reproduced from the pin. Changing model config creates a new version.

A batch execution endpoint

Open question, not yet designed.

Why deferredLoop fan-out over many items is the case that would justify it, but per-item executions keep idempotency, cancellation, and partial-failure semantics simple. Batching changes all three, so it needs its own design rather than being bolted on.

Tool callbacks into Asoar

Open question.

WhyIf agents can call tools that reach external systems, either the platform uses its own connectors or it calls back into Asoar integrations. The second gives one secrets path but needs a two-way protocol, which is a larger contract than this one.
