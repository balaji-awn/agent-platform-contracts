Design note · authoring UI for agent input and output schemas

The Schema Builder

Every agent on the platform declares an input schema and an output schema. Today they are hand-written JSON Schema. This note specifies the UI that lets an author build them from rows in a table — and the rules that turn those rows into a contract Asoar can bind against.

The shape. Two sections, Input and Output, each behind an enable checkbox. Each holds a flat list of fields. Each field is four controls and a toggle: name, varName, description, datatype, required. No nesting, at any depth.

The constraint that drives everything else. varName is not a label. It becomes the JSON Schema property key, which is the name Asoar binds to downstream. Get it wrong and the field is unreachable.

01 What the author sees

One panel, two independent halves

The builder lives on the agent's draft editing screen. Input and Output are symmetrical and independent: an agent may declare both, either, or neither. Each half is collapsed to a single checkbox row until it is enabled.

Why a checkbox rather than "add a field to begin"

An empty list and a deliberately empty schema look identical but mean different things. The checkbox records intent: off means "this agent takes no structured input", which is a publishable statement. An enabled section with no rows is an error, not a shrug.

02 The four controls

Where each one lands in the emitted schema

A row is not a free-form record. Each control has exactly one destination, and two of them are load-bearing for systems far downstream of this screen.

Control Lands at Omitted when Consequence
varName the property key never — mandatory The name Asoar binds to. Changing it after publish breaks every workflow pinned to the old version.
name properties.<varName>.title blank Display label in Asoar's Inputs and Outputs tabs. Never emitted as an empty string.
description properties.<varName>.description blank Read by the model when producing structured output. Functional, not decorative.
datatype properties.<varName>.type never — defaults to string Type-checked by Asoar's publish validator against the upstream node's output.
required membership of required[] unchecked Checked by default. Lets the publish validator reject a node that leaves the field unbound.

The section itself

Section stateEmitted schema
Enabled, one or more rows { type, properties, required, additionalProperties: false }
Enabled, zero rows blocks publish  "Input is enabled but has no fields."
Disabled { "type": "object", "properties": {}, "additionalProperties": false }
No row is required required is omitted entirely, never emitted as []
Disabled does not mean absent

input_schema and output_schema are both in the required list of agent-version-contract.schema.json. A contract that omits either one is invalid. An unchecked box must therefore still emit the empty object schema above.

Datatypes

Version one offers four, all primitive: string, number, integer, boolean. The picker has no array, object, or enum entry. Section 07 covers what that rules out and the order in which to add more.

05 Validation

What the builder refuses, and when

RuleFiresWhy it exists
varName is present on blur It is the property key; there is no schema without it.
varName matches ^[a-z][a-z0-9_]{0,63}$ on blur Asoar's binding reference grammar accepts only [A-Za-z0-9_]+ after the dot. A space or hyphen makes the field unreachable from any workflow.
varName is unique within its section on blur Duplicate keys silently collapse into one property.
name at most 120 characters, description at most 2000 while typing Mirrors the limits the contract already places on the agent's own name and description.
An enabled section has at least one row at publish Distinguishes "no structured input" from an unfinished draft.
Blank name and description are dropped at compile Emitting "" changes the digest, which mints a new version for a field nobody filled in.

Input and output are separate namespaces. A verdict in both is legal and common; the uniqueness check never spans the two sections.

06 Rules from the contract

Five behaviours this UI does not get to choose

The builder sits at the head of a pipeline that ends in a workflow binding. Everything downstream already has a specification, and four of the rules above fall straight out of it.

Both keys are mandatory
The contract lists input_schema and output_schema as required. Disabling a section emits an empty object schema; it never omits the key.
Identifiers must be bindable
The node schema's reference pattern accepts [A-Za-z0-9_]+ after the final dot. The builder enforces a stricter lowercase form so the same name is legal in every position.
The digest must be stable
It is sha256 over the canonical JSON of the two schemas plus limits. Empty strings and empty arrays are real content, so the compiler omits them rather than emitting them.
Published means frozen
Published versions are immutable and workflows pin agent_id@version. The builder is a draft-only editor; opening a published version is read-only.
Row order is the UI's problem
JSON object keys carry no order and canonicalization sorts them. Author-visible ordering has to live in the platform's own draft record, not in the emitted schema.
A consequence worth telling authors about

Because name is emitted as title inside the schema, it sits inside the digest. Correcting a typo in a display label is therefore a new agent version, exactly as if the type had changed.

This is correct — the digest is what lets Asoar detect drift — but it is surprising. The publish confirmation should say what changed, so "I only fixed a label" does not read as a bug.

07 What it cannot express

The builder covers a subset, and that is a deliberate choice

The contract accepts any JSON Schema 2020-12. The builder emits a narrow, flat slice of it. Agents needing more remain valid and can be authored through the API — but they cannot be round-tripped through this screen.

The cost is concrete. The alert-triage agent used throughout this repo's own fixtures and examples is not authorable here: its alert input is an opaque object, and its severity and verdict outputs are enums. Under a primitives-only picker those enums degrade to bare strings and the constraint is lost.

Capabilityv1Cost of leaving it out
enum no Closed value sets become free strings. The most commonly wanted addition, and the one that most improves structured-output reliability.
array no An agent cannot return a list — several IOCs, several recommended actions.
object no No pass-through of an opaque upstream payload such as a whole alert body.
Nested properties no Deliberate and permanent. Flatness is the point of this design, not a v1 limitation.
Numeric and string bounds no Ranges and patterns live in the description as prose, where only the model reads them.
The additive path

Add enum first — a value list on a string row, no layout change beyond one sub-editor. Then array of primitive, which needs only a second type picker for the item type. Then opaque object, a single datatype entry emitting {"type":"object"} with no child rows.

All three are additive to the contract and none disturbs the flat row model, so shipping the primitives-only version first costs nothing later.

08 What to settle

Open questions for the platform team

1 · Does strict mode override the Required toggle?
Some providers' structured-output modes require every property to appear in required with additionalProperties: false. If the platform uses one, the toggle on the output side is decorative and should be hidden rather than silently ignored.
2 · How does the builder open a schema it cannot edit?
An agent authored via the API with enums or nesting has no row representation. Read-only with an explanation, or a full JSON editor as an escape hatch?
3 · Where does row order live?
It cannot live in the schema. Does the draft record gain an order column, or do authors accept alphabetical rendering?
4 · Should labels be inside the digest at all?
Moving title out to platform metadata would stop label edits minting versions — but Asoar renders from the snapshot alone and would lose the labels entirely.
5 · Is there a field-count ceiling?
Flat schemas with very many fields degrade structured-output quality. A soft warning past some count may be worth more than a hard cap.
6 · Does the draft validate against the platform before publish?
The builder can check shape locally, but only the platform knows whether the model config can honour the schema it was given.
