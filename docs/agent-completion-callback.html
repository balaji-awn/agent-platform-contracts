Design note · evaluating an alternative to polling

Completion by Callback

The proposal: the SOAR submits a job to the AI platform and then waits, doing nothing. When the agent finishes it calls a tool the SOAR exposes, which writes the result into the SOAR's database and wakes the workflow. If too much time passes with no call, the SOAR falls back to asking the platform directly.

Assessment. The instinct is right — being told beats asking sixty times. The risk is not in the callback, it is in who makes it. A tool call is something an agent decides to do; completion is something a runtime knows. Keep the callback, but treat it as a nudge to go and look, not as the evidence itself.

01 The idea

Invert who speaks first

Today the SOAR chases the answer: it starts an execution, then checks on it repeatedly until the agent finishes. The proposal turns that around. The SOAR starts the execution and then goes quiet. The agent, on finishing, reaches back through a tool the SOAR publishes — writing its result into the SOAR's database and signalling the paused workflow to continue.

The tool is exposed over MCP (Model Context Protocol), the standard way to give an agent callable capabilities. The AI platform is configured to reach the SOAR's MCP endpoint, and the agent is told it has a "report completion" tool available.

A timeout remains as a safety net: if the expected call never arrives, the SOAR asks the platform what happened, exactly as it would have done all along.

02 How it would run

The path everyone pictures

Nothing about this is exotic. It is the same shape as a webhook, with MCP as the transport and the agent as the caller. The question is what happens on the other paths.

03 What it buys

Four real advantages

Resume latency collapses
With backoff, a result can sit unnoticed for up to the poll ceiling — around 30 seconds. With a callback it is milliseconds. For a workflow with several agent steps in series, that saving compounds.
No status chatter
A five-minute agent costs roughly fourteen status questions under backoff and zero here. Across a large fleet this is a real reduction in requests to the platform.
The agent can say more
A tool call can carry structured output, intermediate findings, or enrichment written straight into the SOAR — things a status endpoint was never going to give you.
It matches how agents already work
Agents call tools constantly. There is no new protocol to invent, no webhook signing scheme, no delivery-retry machinery to build from scratch.

Worth saying plainly: for the ordinary case this design is better than polling on both latency and cost. Everything below is about the cases that are not ordinary.

04 Where it strains

Six failure modes, in rough order of how much they would cost you

The root of most of them

A tool call is an action the agent chooses. Terminal state is a fact the runtime knows. The proposal uses the first as a stand-in for the second.

Everything an LLM does is probabilistic, including deciding whether, when, and how often to call a tool. Control-flow signals inherit that uncertainty the moment they travel this way.

1. The call may simply never come

The agent hits its token budget, errors out, is cancelled by the platform, or just neglects to call the tool at the end of a long chain of reasoning. Nothing arrives. The workflow sits parked until the timeout fires and the fallback query runs.

The consequence is not data loss — the fallback catches it — but note what it means for the build: you still implement the entire polling path. This design is push plus pull, not push instead of pull.

2. The call may arrive before the run is actually over

Tool calls happen during the agent's turn. "I am done" is therefore a statement made from inside the run, before the platform has marked anything terminal. The agent can report success and then keep going — and fail.

3. The call may arrive twice

Model loops, platform-level retries of a failed tool call, or a network timeout where the call actually landed. Without an idempotent apply — keyed by execution and attempt, with duplicates recognised and ignored — the workflow resumes twice, and every downstream step runs twice.

4. The database write and the wake-up must be one act

Store the result, then fail to signal the workflow, and the step hangs until the timeout even though the answer is sitting in the database. Signal first and fail to store, and the workflow resumes looking for a result that is not there. These need to be one transaction, or a durable outbox that retries the second half.

5. The SOAR now runs an inbound endpoint

Something the polling design never needed. Authentication, transport security, tenant scoping, rate limiting, and availability all become live concerns. If the endpoint is mid-deploy when the agent calls, the notification is lost — the fallback again — and if it is reachable from the wider internet, it is now an attack surface. Which leads to the next section.

6. Cancellation and cost get murkier

If the workflow resumes on an early "done" signal, what stops the agent still running behind it? Who cancels it, and is that run still billable? Under polling this is unambiguous: the execution is over when the platform says it is over.

05 The hostile-input problem

The one that matters most in a SOAR specifically

A SOAR reads attacker-controlled text by definition. Phishing bodies, alert payloads, file names, user agents, log lines — the agent's input is largely written by the people you are defending against. Prompt injection is not a hypothetical in this setting; it is the normal weather.

Now give that agent a tool that writes to your database and releases a paused workflow.

Two properties make this worse than it first appears. If the model supplies the identifiers in the tool call, injected text can name a different run or step — letting one alert's agent write into another investigation. And because the call is authenticated as the platform, the SOAR has no easy way to tell a genuine report from an induced one.

Non-negotiable, if you build this

The model must never supply the identity of what it is reporting on. Which run, which step, which attempt — the platform binds those into the call from the execution context, server-side, where the model cannot reach them.

The model supplies only the payload, and the payload is treated the way you would treat any agent output: validated against a schema, never trusted as authority over what happens next.

06 A safer shape

Keep the callback, demote it

Almost all of the difficulty above comes from one decision: letting the notification carry the result and trigger the resume. Change that single thing and the design keeps its advantages while losing most of its risk.

The adjustment

The tool call carries no result and resumes nothing. All it does is schedule an immediate check of that execution.

The SOAR then reads the outcome from the platform by id — the same read it already knows how to do — validates it, stores it, and resumes the workflow through the one path it has always had.

What each failure mode becomes

FailureResult-carrying callbackHint-only callback
Call never arrives Hang until timeout Backoff continues as if nothing happened
Call arrives early, run later fails Systems diverge, workflow acts on a false success Check finds it still running, books another check
Call arrives twice Double resume unless deduplicated Harmless — an extra read
Injected or forged call Forged result enters the database Harmless — an extra read of the real state
Endpoint down at call time Hang until timeout Backoff continues as if nothing happened
Write and wake not atomic Hung step, or resume with no data Does not arise — the callback writes nothing

The cost of this version is one extra round trip to the platform per execution. In exchange, every row in that table becomes uninteresting, the fallback stops being a distinct code path, and an attacker who fully controls the callback can achieve nothing beyond making you perform a read you were going to perform anyway.

Better still, if the platform can offer it

Have the platform's runtime emit the hint when an execution reaches a terminal state, rather than the agent emitting it from inside its own turn.

Same latency benefit, and the model leaves the trust path entirely. The MCP tool then keeps the job it is genuinely suited to: letting the agent write enrichment and intermediate findings during the run.

07 Side by side

Three designs on the dimensions that decide it

  Polling only Agent reports the result Callback as a hint
Resume latency Up to the poll ceiling, ~30s Milliseconds Milliseconds
Requests per 5-min run ~14 reads 0 reads, 1 inbound call 1 read, 1 inbound call
Who decides "it finished" The platform The model The platform
If the signal is lost N/A Hangs until timeout No effect
Duplicate signals N/A Must be deduplicated carefully Naturally harmless
Inbound endpoint needed No Yes, and it is security-critical Yes, but it is low-value to an attacker
Injection blast radius Agent output only Database writes and control flow An unnecessary read
Result paths to build One Two, and both must agree One
Build cost Lowest Highest — polling too, plus ingress, dedupe, atomicity Middle — polling plus a thin endpoint

Read the last row together with the third. The middle column costs the most to build and moves the authority for a control-flow decision into the least predictable component in the system. The right-hand column buys the same latency for one extra read.

08 What to settle

Questions for the platform team, before any of this is built

Can the runtime emit the signal?
If the platform can notify on terminal state itself, the model leaves the trust path and this becomes straightforwardly the best design.
Can identity be bound server-side?
Can the platform inject run, step and execution identifiers into an outbound tool call from its own context, so the model cannot choose or forge them?
How does the endpoint authenticate?
What credential does the platform present, how is it rotated, and can a call be tied to the specific execution it claims to be about?
What is the relationship in time?
Between a tool call made inside a run and the moment the platform marks that execution terminal — and can a run continue, or fail, after such a call?

The second and fourth questions decide whether the middle column is viable at all. The first decides whether you can skip the debate entirely and take the best version.

A design note weighing an alternative to the polling design described in the companion documents. Nothing here has been implemented; the recommendation is the hint-then-verify variant, and the questions in section 8 gate the decision.
