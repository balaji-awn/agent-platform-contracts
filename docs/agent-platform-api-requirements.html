Agent Platform API Requirements

Asoar workflows run agents that live in the agent platform service. This is what the platform has to expose for that to work: the design-time catalog the workflow designer reads, the execution API the Go engine calls at runtime, and the semantics both sides depend on for reproducible, exactly-once, cancellable agent calls.

01 Scope

One caller, two phases

The Asoar backend is the only client of this API. The browser-based workflow designer never calls the platform directly, so platform credentials stay server-side and tenant scoping and catalog caching happen in one place. Every call carries a service credential plus the tenant the work belongs to.

Design time is the workflow author browsing agents, reading an agent version's contract, and running sample executions from the designer. Runtime is the Go engine executing a published workflow: one agent node becomes one execution on the platform, run by a queue worker that may be restarted, retried, or cancelled at any moment.

Immutable versions
Workflows pin agent_id@version. A published version's prompt, model, and schemas never change.
Contract digest
One hash over the schemas and limits lets Asoar detect drift before it publishes a workflow.
Hybrid sync and async
Prefer: wait=N returns the result inline when it is fast, and a 202 to poll when it is not.
Replay-safe writes
A redelivered queue job must never produce a second execution or a second bill.
Explicit retryability
Every error says whether retrying can help. Callers never infer it from the status code.
Throttling signal
Rate-limit headers on every response let Asoar pace its own job queue.

Not required for the first version

  • Completion webhooks. Asoar polls first; callback_url is reserved in the request body.
  • A batch execution endpoint for loop fan-out.
  • Tools that call back into Asoar integrations.

02 Conventions

What holds for every endpoint

R1

Every request carries X-Tenant-ID, and the platform scopes visibility to that tenant.

Agents, versions, and executions a tenant may not see are 404, never 403, so the API does not leak the existence of another tenant's agents.

R2

Responses may grow; requests may not.

The platform may add response fields and new error codes at any time, and Asoar ignores what it does not know. Request bodies are closed: an unknown field is 400 REQUEST_INVALID, which catches typos in generated callers rather than silently dropping them.

R3

Every response, including errors, carries RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset (reset in seconds).

Asoar reads these on execution calls to pace its queue before it starts getting 429s.

Everything is JSON over HTTPS under a versioned base path such as /v1. Authentication today is a bearer service token; whether that becomes OAuth client credentials or a scoped API key, and how the tenant model maps between the two services, is open.

03 Design-time API

The catalog the designer reads

These endpoints back the designer's agent palette, the inline preview, the About tab, and the Test tab. They are also what the publish validator calls to verify a workflow before freezing it.

GET /agents

Lightweight palette list. No schemas in the response.

GET /agents/{agent_id}

Agent metadata for one agent.

GET /agents/{agent_id}/versions

Every version in every status, newest first. Drives the "update available" badge.

GET /agents/{agent_id}/versions/{version}

The full contract: input schema, output schema, limits, digest, model. The source of truth at publish.

POST /agents/{agent_id}/versions/{version}/validate

Check an input against the input schema without executing.

POST /agents/{agent_id}/versions/{version}/test

Sample run from the designer, flagged so it stays out of production metrics.

Listing and filtering

ParameterBehaviour
search Case-insensitive substring match on agent_id, name, or description.
tags Comma-separated. Keeps agents carrying every listed tag.
status published (default) or deprecated. Keeps agents with at least one version in that status.
cursor, limit Opaque cursor; limit 1–200, default 50. next_cursor is null on the last page. Order must be stable across pages.
R4

latest_version is the highest version whose status is published, or null when the agent has none.

The designer pins exactly this version when an author drops an agent on the canvas, so it must never point at a deprecated or disabled version.

R5

Invalid input to /validate is a 200 with valid: false, not an error response.

Each entry in errors carries a JSON Pointer into the input, such as /alert/source, so the designer can mark the offending field.

R6

/test behaves exactly like creating an execution, with four differences: the execution is flagged is_test and excluded from production metrics, there is no idempotency key and no replay, there is no workflow context, and timeout_ms defaults to the version's default_timeout_ms.

04 Runtime API

One agent node, one execution

POST /executions

Start an execution, or replay the one already recorded for this idempotency key.

GET /executions/{execution_id}

Status and result. The polling endpoint.

POST /executions/{execution_id}/cancel

Called when an Asoar run is cancelled or its deadline expires.

GET /executions/{execution_id}/trace

Intermediate steps for the runs view. Optional for the first version.

Request body

FieldRequiredMeaning
agent_idyesThe pinned agent.
agent_versionyesThe pinned version. Integer, at least 1.
inputyesMust conform to that version's input_schema.
contextyesworkflow_id, run_id, node_path, and optional attempt. Echo it into traces and billing records so a cost can be traced back to a workflow run.
timeout_msyesPer attempt, measured from execution creation. Above max_timeout_ms is a 400.
callback_urlnoReserved for the planned completion webhook.
R7

Honour Prefer: wait=N: hold the request open up to N seconds for a terminal state, then answer 200 with the execution. If it is still running, answer 202 with the execution_id and a Location header.

Parse it as RFC 7240, so respond-async, wait=20 works and unknown preferences are ignored. Without wait the platform does not block. The server may cap N and reports what it applied in Preference-Applied.

Order of checks

Each of these refuses the request before an execution exists, which matters because a rejected request leaves the idempotency key free for a retry.

  1. Auth and tenant — 401, 403, or 400 for a missing tenant header.
  2. Missing or oversized Idempotency-Key, or a malformed body — 400 REQUEST_INVALID.
  3. Idempotent replay — see section 7. Checked before the version exists, so a replay still works after a version is disabled.
  4. Unknown or invisible version — 404. Disabled version — 409. Deprecated versions still execute.
  5. timeout_ms above max_timeout_ms — 400 with a details entry for /timeout_ms.
  6. Input that fails the input schema — 400 INPUT_SCHEMA_INVALID with per-field details.
  7. Admission refused — 429 or 503 with retry_after_ms.
R8

When timeout_ms elapses, the execution fails with TIMEOUT and retryable: true, and the platform stops billing work for it.

R9

Cancel is idempotent. A queued or running execution moves to cancelled; a terminal one comes back unchanged. A cancelled execution has no error.

Asoar calls this when a run is cancelled and when its own deadline expires, so it may arrive at any point, including for an execution that just finished.

R10

The platform guarantees output conforms to the version's output_schema for a succeeded execution, using structured output plus an internal repair loop.

Asoar re-validates as defence in depth and treats a violation as a non-retryable node failure, so a schema break surfaces as a workflow error rather than corrupt downstream bindings.

05 Version contract

What a pinned version promises

GET /agents/{id}/versions/{v} returns the contract that Asoar snapshots into the workflow node and re-verifies at publish. Its shape is fixed by schemas/agent-version-contract.schema.json in the contract repo.

FieldNotes
agent_id, version, nameIdentity. description, tags, and owner are optional and shown in the designer.
statuspublished, deprecated, or disabled.
deprecationOptional since, replacement_version, and message, shown when an author opens a deprecated pin.
input_schema, output_schemaJSON Schema 2020-12, the same dialect Asoar uses for its own action schemas so one binding and validation path serves both.
limitsdefault_timeout_ms, max_timeout_ms, and optional recommended_max_attempts. The designer pre-fills execution settings from these and rejects anything above the max.
modelProvider, name, temperature, max tokens. Read-only in the designer and deliberately excluded from the digest.
digest, published_atSee below.
R11

A published version is immutable. Any change to prompt, model, temperature, or either schema creates a new version.

This is what makes a workflow run reproducible: a published Asoar workflow keeps calling the exact version it was published against, and upgrading is an explicit author action.

R12

digest is sha256: followed by the lowercase hex SHA-256 of the RFC 8785 canonical JSON of {input_schema, output_schema, limits}, computed over the JSON exactly as served.

Model details are excluded on purpose, so the digest tracks only what callers bind against. Asoar stores it in the node and compares it at publish; a mismatch blocks the publish rather than silently breaking bindings.

Status lifecycle

StatusExecutesEffect in Asoar
published yes Pinnable. The only status a workflow can be published against.
deprecated yes Existing runs keep working. The designer warns and blocks new pins.
disabled no Executions rejected with 409 AGENT_VERSION_DISABLED, a non-retryable node failure.

06 Error model

Two channels, one retry decision

A request-level rejection means no execution was created: a non-2xx status carrying {"error": {...}}, and the idempotency key stays free. An execution-level failure means the execution exists and reached status: failed: HTTP 200 carrying the execution with its error set. A failed execution is never an error response, including when it fails inside the Prefer: wait window.

R13

Every error carries code, message, and an explicit retryable boolean.

Asoar decides retries from the flag alone. Retryable failures consume a node attempt and get the backoff; non-retryable ones skip the remaining attempts and go straight to the node's on-error behaviour, because a schema error fails identically every time and would just burn attempts.

R14

Retryable errors carry retry_after_ms, which is authoritative. The Retry-After header, rounded up to whole seconds, is for intermediaries.

QUOTA_EXCEEDED covers both the tenant's quota and the advertised request rate limit. Because the platform absorbs transient provider errors internally, a PROVIDER_* failure that reaches Asoar is terminal for that execution.

Validation errors carry details: a list of {path, message} where path is a JSON Pointer into the input for schema errors, or into the request body for everything else.

07 Idempotency

The requirement that carries the most weight

Asoar's engine runs on a durable job queue. A worker can die mid-execution and the job will be redelivered; that redelivery must not start a second LLM run or produce a second bill. Asoar builds the key from run_id + node_path + attempt, so a redelivery reuses the key while a deliberate retry increments attempt and therefore gets a fresh one.

R15

Idempotency-Key is required on every POST /executions and is scoped to the tenant.

R16

A repeat of the same key with the same JSON body returns the recorded execution in its current state and starts nothing.

Bodies are compared as JSON values after RFC 8785 canonicalization, so key order and whitespace do not matter. The replay honours Prefer: wait again, which is what lets a redelivered job simply wait for the original execution to finish.

R17

The same key with a different body is 409 IDEMPOTENCY_KEY_REUSED.

That is a bug signal, not a retry: it means two different node inputs collided on one key.

R18

Keys are retained for at least 24 hours after the execution is created, and a request-level rejection does not record the key.

The retention window is a proposal — confirm what the platform can actually hold, since it bounds how long a queue job may be delayed and still be replay-safe.

09 Open questions

What we need from the platform team

These block or reshape parts of the contract above. The first one gates everything else, since this spec was written from Asoar's requirements rather than from the platform's current routes.

Q1 · gating

Which of these endpoints exist today, and where does the real shape differ from this document?

Q2 · auth

OAuth client credentials or a scoped API key? And how does the tenant model map between the two services — is X-Tenant-ID trusted from the caller, or derived from the credential?

Q3 · idempotency

How long can recorded keys actually be retained (R18 proposes 24 hours)?

Q4 · webhooks

When can execution.succeeded/failed/cancelled and version lifecycle events land? Catalog cache invalidation and parking long executions both depend on them.

Q5 · batch

Is a batch execution endpoint needed for loop fan-out over many items, or is per-item execution acceptable?

Q6 · tools

If agents can call tools that reach external systems, do those use the platform's own connectors, or call back into Asoar integrations?

Q7 · billing

cost_usd is currently a float. Integer micro-USD would avoid rounding drift in per-run cost rollups — worth changing before anyone depends on it.

Q8 · limits

What are the real rate limits and quota units per tenant, and which RateLimit header draft should we standardise on?

Acceptance

The contract repo ships a mock platform and a Go client that implement this document. A platform build is conformant when the same integration suite passes against it: sync success, slow success followed by polling, retryable and non-retryable failures, a timeout, a cancellation, a redelivered request producing exactly one execution, and a reused key with a changed body returning 409.
